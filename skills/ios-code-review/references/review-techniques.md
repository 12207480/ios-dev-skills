# 审查技巧与沟通

## 提问法：用问题替代直接指出错误

用问题引导作者自己发现问题，比直接批评更容易被接受，也能激发更深入的思考。

### 示例对比

| 直接指出（❌ 偏对抗） | 提问引导（✅ 偏协作） |
|-------|-------|
| "items 为空会崩溃" | "如果 items 是空数组会怎样？" |
| "你没做版本检查" | "这个 API 在 iOS 15 上的行为是什么？" |
| "这里有循环引用" | "这个闭包的生命周期是怎样的？会不会持有 self？" |
| "错误处理不完整" | "当网络请求失败时，用户会看到什么？" |
| "这个命名有歧义" | "第一次看到这个方法名，能猜到它的作用吗？" |

### 适用场景

- 逻辑缺陷但不确定作者是否有意为之
- 设计决策你不理解动机时
- 想让作者考虑边界情况时
- 代码意图不明确时

### 不适用场景

- 明确的崩溃 Bug → 直接指出并标注 🔴 Must Fix
- 违反项目明确规范 → 直接说明规范要求

## 建议而非命令

### 示例对比

| 命令式（❌） | 建议式（✅） |
|---------|---------|
| "必须改成 async/await" | "考虑用 async/await 是否更清晰？" |
| "提取这个方法" | "这个逻辑出现了 3 次，提取为方法是否合理？" |
| "用 guard 替换 if let" | "这里用 guard 提前返回是否能减少嵌套？" |
| "删除这段注释" | "这段注释和代码描述的行为不一致，可以确认一下吗？" |

### 协作语言模板

```
建议类：
  "考虑..."
  "是否可以..."
  "另一种方式是..."
  "你觉得...怎么样？"

讨论类：
  "我理解你的做法是...，不过我有个疑问..."
  "这里的取舍是什么？我倾向于...，因为..."
  "我之前在类似场景中用过...，供参考"

肯定类：
  "这个封装做得很好，特别是..."
  "学到了一种新写法，很简洁"
  "处理得很周到，边界情况都考虑到了"
```

## 反馈写作原则

### 好的 Review 评论

```
✅ 指出具体问题 + 解释为什么是问题 + 给出建议方案
✅ 对事不对人（"这段代码"而非"你的代码"）
✅ 用事实和文档支撑观点（"根据 Apple 文档..."）
✅ 区分主观偏好和客观问题
✅ 对复杂问题提供代码示例
✅ 先肯定做得好的地方，再提出改进建议
```

### 坏的 Review 评论

```
❌ "这样不行" — 没有解释为什么
❌ "我觉得应该用 X" — 没有说明理由
❌ "这样写不好看" — 纯主观且无建设性
❌ 大量 nit 淹没了关键问题 — 优先级不分
❌ 只批评不提供替代方案 — 不可操作
❌ "为什么不用 X？" — 暗含指责，改为"这里用 X 是否更合适？因为..."
```

## 审查效率技巧

### 推荐阅读顺序

```
1. PR 描述和评论 → 理解全貌
2. 数据模型（Model）→ 理解数据结构变化
3. 服务层（Service/API）→ 理解数据来源变化
4. 逻辑层（ViewModel）→ 理解业务逻辑变化
5. 视图层（View/VC）→ 理解展示变化
6. 测试文件 → 确认覆盖度
7. 配置文件（Info.plist/Podfile 等）→ 确认无意外变更
```

### 效率原则

```
- 先整体后细节：先看文件列表，再逐文件看代码
- 先理解后评判：先懂为什么改，再说改得对不对
- 先关键后次要：先看 Must Fix，再看 Nit
- 批量反馈：一次看完再提交所有评论，不要边看边发
- 控制 Nit 数量：如果 Nit 超过 5 条，只保留最重要的 3 条
```
