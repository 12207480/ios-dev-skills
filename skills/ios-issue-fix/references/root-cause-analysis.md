# 根因分析与上下文关联

## 代码定位策略（按问题类型）

| 问题类型 | 定位路径 |
|---------|---------|
| UI 显示异常 | 设计稿/截图 → 页面类名 → ViewController/SwiftUI View → 具体 UI 组件 → 布局代码 |
| 功能逻辑错误 | 用户操作入口 → Button Action/Delegate/Closure → 沿调用链 View → ViewModel → Service → Model |
| 数据问题 | 数据展示 UI → 向上追溯 UI ← ViewModel ← Service ← API/本地存储 → 逐层确认 |
| 交互异常 | 手势/事件处理代码 → 响应链(hitTest/pointInside) → 动画代码 → 导航代码 |

## 理解原有代码意图（5 步检查法）

**在修改任何代码之前，必须先理解它为什么这样写。**

1. **这段代码的职责是什么？** — 它解决什么问题？属于哪个模块？注释和命名是否透露了设计意图？
2. **数据从哪来，到哪去？** — 输入参数是谁提供的？输出结果被谁消费？有没有异步/跨线程的数据传递？
3. **谁在调用它？** — 全局搜索函数名/类名，找到所有调用方。检查 protocol/delegate/notification/KVO 的隐式调用，以及 Storyboard/XIB 中的 IBAction/IBOutlet 连接。
4. **它和其他模块的关系？** — 是否依赖全局状态（单例/AppDelegate/全局变量）？是否被其他页面复用？修改是否需要同步修改调用方？
5. **有没有相关的测试？** — 搜索对应的 Tests 文件。已有测试覆盖了哪些场景？缺失的测试恰好是 Bug 所在的场景吗？

## 关联变更历史（Git 命令）

```bash
# 查看出问题代码的最近变更
git log -10 --oneline -- <文件路径>
git log -p -1 -- <文件路径>    # 查看最近一次改了什么

# 如果 Issue 标注了"之前是好的"
git log --since="2024-01-01" -- <文件路径>
git bisect start                # 二分法定位问题 commit

# 查看相关文件的关联变更
git log --oneline -- <目录>     # 查看模块整体变更记录
```

阅读问题 commit 的 PR/MR 描述，理解当时为什么做这个改动：是新功能引入的副作用？还是修复其他 Bug 时的连带问题？

## 影响范围图模板

```
问题定位：
  文件：[具体文件路径:行号]
  函数：[具体函数名]
  根因：[一句话描述代码层面的原因]

上游影响（谁调用了这段代码）：
  1. [调用方 A — 页面/模块名]
  2. [调用方 B — 页面/模块名]

下游影响（这段代码依赖了什么）：
  1. [依赖 A — API / 本地存储 / 第三方 SDK]
  2. [依赖 B — 公共组件 / 工具类]

关联组件（修改可能波及的其他地方）：
  1. [组件 A — 原因]
  2. [组件 B — 原因]
```

**关键原则：** 影响范围不清楚就不动手。修复一个 Bug 引入两个新 Bug 是最差的结果。

## 通用根因追溯法

1. **锚定差异点** — 预期值是 A，实际值是 B，找到代码中产生值 B 的那行代码
2. **反向追溯** — 这个值从哪里来？向上追溯一层，持续追溯直到找到"首次出现错误值"的位置
3. **定位根因** — 是输入就是错的（数据源）？中间转换错了（逻辑）？时序不对（生命周期）？并发覆盖（线程安全）？
4. **一句话描述根因** — "因为 X，导致 Y，所以用户看到了 Z"。如果说不出这句话，说明还没找到根因

**永远不要只在错误表现的地方修复。症状在 View 层，根因可能在 Service 层。**

## 并发问题根因追溯

并发 Bug 通常表现为"偶现"、"只在某些设备上出现"、"加断点就消失"，需要特殊的排查思路：

### 数据竞争定位
1. **开启 Thread Sanitizer (TSan)** — Scheme → Diagnostics → Thread Sanitizer
2. 复现问题 → TSan 会标记出竞争的具体变量和两个线程的调用栈
3. 确认竞争变量 → 用 `actor` / `@MainActor` / 串行队列保护

### actor reentrancy 导致的状态不一致
1. 在 actor 方法的每个 `await` 前后打印状态值
2. 如果 await 后状态被其他调用者修改 → 这就是 reentrancy
3. 修复：await 后重新读取状态，不要依赖 await 前的假设

### Task 泄漏导致的幽灵回调
1. 页面销毁后仍有代码执行 → 检查 Task 是否被正确取消
2. 在 `deinit` / `onDisappear` 中打印日志确认清理时机
3. 检查 `task {}` modifier 是否绑定在正确的视图层级
