# 需求分析

## 需求类型判断

先判断需求属于哪种类型，不同类型的关注点不同。

> 完整的需求类型判断表见 SKILL.md，此处聚焦各类型的深入分析流程。

### 各类型深入分析

**全新功能：**
- 确认模块边界和职责划分
- 技术选型是否需要引入新框架或依赖
- 与现有模块的集成方式（导航入口、数据共享、事件通知）
- 参考项目中类似模块的目录结构和架构模式

**功能增强：**
- 现有代码的扩展点在哪里（protocol、delegate、通知）
- 新增行为是否与现有行为互斥
- 是否需要修改现有接口签名（影响所有调用方）
- 增强后是否需要向下兼容（旧版本 App、旧数据格式）

**功能修改：**
- 列出所有依赖旧行为的调用方
- 新旧行为的差异矩阵（输入/输出/副作用）
- 是否需要渐进式迁移（Feature Flag、A/B Test）

**交互优化：**
- 设计稿中每个交互状态的细节（hover、press、disabled、loading）
- 动画参数（时长、曲线、延迟）
- 手势冲突检测（与系统手势、与已有自定义手势）
- 无障碍影响评估

**数据/接口调整：**
- 新旧字段映射关系表
- 本地缓存数据迁移方案
- 旧版本客户端兼容策略
- 数据校验规则变更

## 需求信息提取模板

从 PRD / 需求文档 / 口头沟通 / 设计稿中逐项提取：

```
【功能概述】一句话概括做什么
【需求类型】全新 / 增强 / 修改 / 优化 / 适配
【关联的现有功能】这个需求和项目中已有的哪些功能相关？
【核心流程】用户从哪里进入 → 执行什么操作 → 得到什么结果
【输入/输出】需要什么数据？产生什么数据？数据从哪来到哪去？
【状态流转】涉及哪些状态变化？新增状态还是修改现有状态流转？
【异常场景】网络失败？数据为空？权限拒绝？超时？中途退出？
【非功能要求】性能？离线？无障碍？国际化？
【不做什么】明确排除的范围
【验收标准】怎样算"做完了"？
```

## 设计稿审阅清单

逐屏检查（对增量需求尤其要关注变化部分）：

**新增的 UI：**
- 在哪个页面的什么位置新增？
- 导航方式是什么？（Push / Present / Tab / 嵌入已有页面）
- 交互细节：点击/滑动/手势分别触发什么？
- 状态变体：加载中 / 空 / 错误 / 正常 各是什么样？
- 视觉规范：字体/颜色/间距/圆角的具体值

**修改的 UI：**
- 哪些元素被修改了？（对比新旧设计稿）
- 修改是否影响现有页面的布局结构？
- 修改后是否与相邻页面的风格一致？

**未变化的 UI：**
- 确认设计稿中没提到的地方是否真的不需要改
- 新增功能是否需要在现有页面增加入口？

**设计稿与 PRD 的不一致之处：**
- 记录每一处矛盾，编码前必须确认

## API 审阅清单

逐接口检查：

1. 新增接口还是修改现有接口？
2. 请求方式/路径/参数/响应结构
3. 与现有接口的关系（共用模型？依赖调用顺序？）
4. 分页/错误码/频率限制
5. 接口是否已就绪？还是需要 Mock？
6. 现有 Codable 模型是否需要修改？修改后影响其他页面吗？

## 输出模板

### 需求理解卡片

```
需求：[一句话概述]
类型：[全新 / 增强 / 修改 / 优化 / 适配]
关联功能：[列出相关的现有功能模块]
变化点：[具体改了什么/加了什么]
验收标准：[怎样算完成]
```

### 疑问清单

```
Q1: [具体问题]
    背景：[为什么有这个疑问]
    建议：[你的建议方案]
    需要谁确认：[产品 / 设计 / 后端 / QA]
```

**关键原则：** 疑问清单必须在写代码前关闭。特别是增量需求，"这个改动要不要影响已有功能"这类问题必须提前确认。
